# HARA-001: 위험 분석 및 리스크 평가 (Hazard Analysis and Risk Assessment)

| 항목 | 내용 |
|---|---|
| 문서 ID | HARA-001 |
| 상태 | Draft (템플릿 — 워크드 예시 1건 + stub) |
| 버전 | 0.1 (개정이력은 §7) |
| 참조 표준 | ISO 26262-3:2018 (Concept phase / HARA) |
| 관련 산출물 | SRS-001(NFR-SAFE-001~004, FR-DRV-003, FR-SEN-002, FR-AB-001~008), TARA-001 |
| 적용 한계 | 본 플랫폼은 2WD RC 데모. 아래 등급은 **표현(represented) 차량 기능 기준**으로 부여하고, 실제 RC 실물의 물리 심각도는 별도 주석(§3 비고)으로 구분한다. |

> **목적.** "기능이 고장·오작동했을 때 사람에게 가는 해(harm)"를 차량 레벨에서 식별하고, S/E/C로 등급화해 **ASIL과 Safety Goal**을 도출한다. SRS의 안전 요구(NFR-SAFE-*, FR-AB-*)는 *여기서 유도된 결과*여야 한다. (적이 있는 의도적 공격은 [TARA-001](TARA-001_Threat_Analysis_Risk_Assessment.md)에서 다룬다.)

---

## 1. 아이템 정의 (Item Definition)

HARA의 *입력*. 위험을 분석하려면 대상의 경계·기능·동작조건이 먼저 고정돼야 한다.

| 항목 | 내용 |
|---|---|
| 아이템 | 버튼 트리거 직진 주행 + 장애물 정지 차량 (DriveECU + SensorECU + CAN) |
| 주요 기능 | F1: 버튼 입력 시 직진 출발 / F2: 전방 장애물 10cm 감지 시 정지 / F3: A/B Secure OTA 업데이트 |
| 경계 | DriveECU(모터제어), SensorECU(HC-SR04), CAN 0x100/0x200/0x201, 부트로더. Gateway(RPi5)는 외부 |
| 동작 모드 | 부팅(BL) / IDLE / 주행 / OTA 다운로드 / OTA 활성화(재부팅) |
| 외부 인터페이스 | B1 버튼, HC-SR04, TB6612FNG 모터, CAN 버스 |

## 2. 등급 척도 (ISO 26262-3)

**S — 심각도 (Severity)**

| 등급 | 의미 |
|---|---|
| S0 | 부상 없음 |
| S1 | 경상~중경상 (AIS 1, 회복 가능) |
| S2 | 중상, 생존 가능 (AIS 3~6) |
| S3 | 치명상/사망 가능 (AIS 5~6) |

**E — 노출 빈도 (Exposure, 해당 동작상황에 놓일 확률)**

| 등급 | 의미 | 예 |
|---|---|---|
| E1 | 매우 낮음 | 거의 발생 안 함 |
| E2 | 낮음 | 드물게 |
| E3 | 중간 | 운전 중 가끔 |
| E4 | 높음 | 거의 매 주행 |

**C — 제어 가능성 (Controllability, 운전자/외부가 해를 회피 가능한가)**

| 등급 | 의미 |
|---|---|
| C0 | 일반적으로 제어 가능 |
| C1 | 쉽게 제어 가능 (99% 이상) |
| C2 | 보통 제어 가능 (90% 이상) |
| C3 | 제어 어려움/불가 |

**ASIL 결정 (ISO 26262-3:2018 Table 4).** 앵커: **S3·E4·C3 = D**. S·E·C 중 하나가 한 단계 낮아질 때마다 ASIL 한 단계 ↓ (하한 QM).

| S·E | C1 | C2 | C3 |
|---|:--:|:--:|:--:|
| **S3·E4** | B | C | **D** |
| S3·E3 | A | B | C |
| S3·E2 | QM | A | B |
| **S2·E4** | A | B | C |
| S2·E3 | QM | A | B |
| S2·E2 | QM | QM | A |
| **S1·E4** | QM | A | B |
| S1·E3 | QM | QM | A |

> 표에 없는(더 낮은) 조합은 QM. QM = 표준 품질관리로 충분, 별도 ASIL 안전요구 불필요.

## 3. HARA 분석표

각 행 = 한 위험 사건. **Safety Goal**이 최상위 안전요구이고, 거기서 FSR→SW 안전요구로 내려간다(§4).

| ID | 기능 | 동작상황 | 오작동 | 위험 사건 (차량 레벨 harm) | S | E | C | **ASIL** | Safety Goal | Safe State | FTTI |
|---|---|---|---|---|:--:|:--:|:--:|:--:|---|---|---|
| **H-1** | F2 장애물 정지 | 저속 직진 주행 중 전방 장애물 접근 | 장애물 감지 실패 또는 모터 미정지 | 차량이 장애물/보행자와 충돌 | S2 | E4 | C3 | **C** | 전방 10cm 장애물 감지 시 차량은 충돌 전 정지해야 한다 | 모터 정지 (NFR-SAFE-004) | 감지~정지 ≤ Tstop *(실측 유도)* |
| H-2 | F3 OTA 활성화 | 주행 중 OTA 활성화 조건 충족 | 주행 중 의도치 않은 재부팅/제어 상실 | 주행 중 갑작스런 거동/정지 불능 | _TODO_ | _TODO_ | _TODO_ | _TODO_ | OTA 활성화(재부팅)는 IDLE에서만 발생해야 한다 | 모터 정지 + 활성화 보류 | ← NFR-SAFE-001, FR-DRV-008 |
| H-3 | 부트로더 | 부팅(BL 실행) 단계 | BL 단계에서 모터 PWM 활성 | 부팅 중 의도치 않은 차량 이동 | _TODO_ | _TODO_ | _TODO_ | _TODO_ | 부트로더 실행 중 모터는 구동되지 않아야 한다 | 모터 출력 비활성 | ← NFR-SAFE-003 |
| H-4 | F3 A/B Slot | 업데이트/전원차단 후 첫 부팅 | 손상·미검증 이미지로 부팅 → 제어 로직 오류 | 차량 제어 불능 | _TODO_ | _TODO_ | _TODO_ | _TODO_ | 검증 통과한 이미지만 Boot Target이 된다(fail-closed) | 기존 Confirmed Slot 유지/Safe State | ← FR-AB-003, NFR-SAFE-004 |

**H-1 등급 근거 (워크드 예시):**
- **S2** — 저속 충돌이라도 보행자/사람 대상 시 중상 가능. *(RC 실물 비고: 경량 2WD·사람 없음 → 실제 S0~S1. 아래는 표현 기능 기준.)*
- **E4** — "장애물을 향해 접근하며 정지가 필요한 상황"은 이 차량 주기능이라 거의 매 주행 발생.
- **C3** — 본 설계는 운전자 개입 루프가 없는 자동 정지. 안전기능 실패 시 외부 회피 불가.
- → 표에서 **S2·E4·C3 = ASIL C**.

> ⚠️ Tstop(FTTI)·10cm·3-strike·8s IWDG 같은 **숫자는 여기 Safety Goal에서 유도**돼 SRS로 내려가야 한다. 지금 SRS는 이 숫자를 *선언*만 하고 있음 — 그 뿌리를 이 표가 채운다.

## 4. Safety Goal → 요구 내려보내기 (V의 왼쪽)

H-1을 끝까지 한 줄로 내려본 예시. **고도가 낮아지며 구체화**된다.

| 고도 | 항목 | 내용 | 추적 |
|---|---|---|---|
| 위험 사건 | H-1 | 장애물 충돌, ASIL C | 본 문서 §3 |
| **Safety Goal** | SG-1 | 10cm 장애물 감지 시 충돌 전 정지 | — |
| 기능안전요구(FSR) | FSR-1.1 | SensorECU는 ≤10cm 감지 시 CAN 0x200으로 통보 | FR-SEN-002 |
| FSR | FSR-1.2 | DriveECU는 장애물 통보 수신 시 모터를 정지한다 | FR-DRV-003 |
| **SW 안전요구(TSR)** | TSR-1.1 | `drive_update()` 주기 ≤ 10ms | NFR-PERF-003 |
| TSR | TSR-1.2 | 0x200 신호에 Alive Counter+CRC(E2E)를 적용해 stale/손상 프레임을 검출하고 검출 시 Safe State 진입 | **신규 — SRS에 없음** |
| 설계/구현 | — | `motor_stop()`, 상태머신 | (구현 단계) |
| **검증(V 오른쪽)** | TC | 단위: flag 시 motor_stop 호출 / 통합: 0x200→정지 ≤200ms / 적격성: 실차 정지 | TC-DRV-003 |

> **드러난 갭:** TSR-1.2(E2E 보호)는 HARA를 돌려야 비로소 나온다 — 안전 관련 신호인 장애물 프레임에 freshness/CRC가 없으면 "센서가 죽어 마지막 '장애물 없음'을 붙들고 있을 때" 차가 못 선다. 이게 "톱다운 유도가 새 요구를 만든다"의 구체적 증거.

## 5. 안전↔보안 브리지

H-1/H-2의 일부 원인은 *고장*이 아니라 *공격*일 수 있다 (예: 변조 펌웨어로 모터 폭주). 그 경로는 [TARA-001](TARA-001_Threat_Analysis_Risk_Assessment.md)의 피해 시나리오로 연결되며, **TARA의 Safety 영향 등급은 본 HARA의 위험 사건을 참조**한다. 보안 침해 → 안전 위험의 전이가 이 프로젝트의 핵심 논지다.

## 6. 채우는 순서 (사용법)

1. §1 아이템 정의를 네 시스템에 맞게 확정.
2. §3에서 동작모드별 오작동을 브레인스토밍 → 위험 사건(차량 레벨 harm)으로 표현.
3. 각 사건에 S/E/C 부여 + **근거 한 줄**(H-1처럼). 근거 없는 등급은 무효.
4. §2 표로 ASIL 산출 → Safety Goal 작성(+Safe State+FTTI).
5. §4처럼 각 Goal을 FSR→TSR로 내려 **기존 SRS ID에 연결**. 연결 안 되면 그 요구는 근거 없는 것 → SRS 보완 대상.
