## 1. Context (상황 · 문제 · 판단 기준)

초기 `Jenkinsfile`은 `git push` 한 번으로 **변경감지 → 단위테스트 → 정적분석 → 빌드 → 서명 → ECU 플래싱**까지 한 파이프라인에서 일괄 수행했다. 즉 `main`에 머지/푸시되는 **모든 커밋이 즉시 실차(데모 RC) ECU에 기록**된다.

문제의 본질은 `git push`가 트리거인 것이 아니라(그건 CI 트리거로 정석이다), **CI(코드 검증)와 Deployment(차량 배포)를 한 덩어리로 결합**한 것이다. 양산 OTA에서 이 둘은 별개 단계이고, 그 사이에 **릴리스 승인**이 존재한다.

- **UN R156 (UNECE WP.29, SUMS)**: 제조사는 Software Update Management System을 갖추고, *각 업데이트마다* 대상 차량 식별 · 형식승인 영향(RxSWIN) 평가 · 안전성 평가 · **승인**을 문서화해야 한다. "푸시=배포"는 이 승인 기록을 구조적으로 가질 수 없다.
- **Uptane**: **Image Repository**(오프라인 키로 이미지를 서명 — CI 산출물에 대응)와 **Director Repository**(온라인, 차량별 설치 지시 — 배포 결정에 대응)를 분리해, *온라인/CI가 침해돼도 피해를 봉쇄*한다. git이 곧 배포 트리거이면 git 한 곳의 침해가 fleet 전체로 전파된다(blast radius).
- **ASPICE SUP.10 (변경요청관리) / 릴리스 프로세스**: 릴리스 후보 · 스테이징 · 승인 없이 머지가 곧 배포이면 변경통제(change control)가 없다.
- **ISO 24089 (Road vehicles — Software update engineering)**: 업데이트 캠페인 · 패키지 · 승인을 구분된 개념으로 정의한다.

**Decision Drivers (판단 기준)**
1. 승인 · 추적성 (UN R156 SUMS / ASPICE)
2. 보안 blast-radius 최소화 (Uptane Image/Director 분리)
3. 릴리스 의도의 명시성 · 불변성
4. Raspberry Pi 단일 노드 데모에서의 구현 공수

## 2. Considered Options (검토한 옵션)

### 옵션 A — 현행(결합): push가 빌드~플래싱까지 일괄
- **장점**: 파이프라인 전체가 한 번에 도는 걸 데모로 보여줌, 추가 공수 0.
- **한계**: 승인 게이트 부재(UN R156 위배), CI 침해 = fleet 침해, 릴리스/스테이징 개념 없음, 모든 머지가 실차에 기록됨.

### 옵션 B — SSH 수동 실행: 개발자가 Pi에 접속해 `ota_client.py`를 직접 실행
- **장점**: 사람이 개입(deliberate).
- **한계**: 감사 기록 · 재현성 없음, "승인"이 아니라 단순 접근통제, 휴먼에러 · 비확장. ASPICE 추적성 위배 → 결합보다 오히려 후퇴.

### 옵션 C — CI/배포 분리 + 태그 릴리스 + 승인 게이트 (채택)
- `push`(브랜치): 단위테스트 · 정적분석 · 컴파일 검증까지만. **ECU 미접촉.**
- `태그 vN`(릴리스): 빌드 + ECDSA 서명(version=N) + 아티팩트 보관 → Uptane *Image Repository* 행위.
- **승인 게이트**(`input`): 승인자 기록 → UN R156 승인의 미니어처.
- `Deploy`: 승인 후, *사전 서명된* 아티팩트를 live 활성슬롯 반대편에 전송 → 슬롯 전환 검증 → Uptane *Director*/캠페인 행위.
- **장점**: 세 단계 분리, 릴리스 의도(태그)가 불변이며 버전 출처가 됨, 승인 감사, 배포 단계는 개인키 불필요.
- **한계**: Pi가 여전히 Image/Director/Gateway 3역을 겸함(양산은 분리), `input`이 단일 executor를 점유.

---

## 3. Decision (결정 · 근거)

**옵션 C를 채택한다.**

- **태그를 릴리스 마커 겸 버전 출처로 사용**: `vN` 정규식 매칭 → `RELEASE_VERSION=N`을 `sign_firmware.py --version N`에 주입한다. 이는 anti-rollback 기준선(ADR-007)을 실제로 증가시킨다. (기존 파이프라인은 `--version`을 전달하지 않아 모든 이미지가 version=1로 서명 → 기준선이 정체되는 잠재 버그가 있었고, 태그 기반으로 해소된다.)
- **태그 = 배포 자격(eligibility), 승인 = 실행 권한(authority)의 2요소**: 태그가 "이것이 의도된 릴리스"임을, `input` 승인이 "지금 이 ECU에 꽂을 권한"을 각각 표현한다. 실무에서 릴리스 관리와 캠페인 배포가 다른 결정인 것을 데모 규모로 축소 구현한 것이다.
- **build-all / deploy-select**: 릴리스 시 A·B 두 슬롯 변형을 모두 빌드·서명·보관하고, 배포 단계는 live 슬롯을 읽어 *재빌드·재서명 없이* 해당 아티팩트를 선택한다. 슬롯 결정이 빌드타임이 아니라 배포타임 관심사임을 반영하고, 배포 단계에서 개인키를 제거한다.

## 4. Consequences (결과 · 트레이드오프 · 한계)

| 판단 기준 | A 결합 | B SSH | C 분리(채택) |
|---|:---:|:---:|:---:|
| 승인 · 추적성 (UN R156 / ASPICE) | ✗ | ✗ | ✓ |
| 보안 blast-radius 최소화 | ✗ | △ | ✓ |
| 릴리스 의도 명시 · 불변 | ✗ | ✗ | ✓ |
| 배포 단계 개인키 불필요 | ✗ | ✗ | ✓ |
| 구현 공수 | ✓ | ✓ | △ |

**받아들인 한계 / 개선 경로**
- Pi가 Image + Director + Gateway 3역을 겸한다 — 양산에선 백엔드 캠페인 서버와 차량 TCU로 분리된다(데모 제약, ADR-001 §3과 동일 맥락).
- `input` 승인 대기 동안 `agent any` executor를 점유한다. 단일 노드 데모라 허용하며, 멀티 노드 환경에선 `agent none` + per-stage agent로 개선한다.
- 캠페인 객체(SR-UP-003: 복수 ECU partial/fail 추적)는 아직 stage 단위 로그 수준이다 — manifest 기반 `campaign_id` 기록은 후속 과제.
- 서명 헤더 `target_ecu_id` 주입 및 ECU 측 ID 불일치 검증(FR-CAN-011 / SR-FW-004)은 본 ADR 범위 밖이며 별도 과제로 둔다.
