# HARA-001: 위험 분석 및 리스크 평가 (Hazard Analysis and Risk Assessment)

| 항목 | 내용 |
|---|---|
| 문서 ID | HARA-001 |
| 상태 | 분석 완료 (H-1~H-4 · ASIL·SG·검증 연결) |
| 버전 | 1.0 (개정이력은 §7) |
| 참조 표준 | ISO 26262-3:2018 (Concept phase / HARA) |
| 관련 산출물 | SRS-001(NFR-SAFE-001~004, FR-DRV-003, FR-SEN-002, FR-AB-001~008), TARA-001, SIT-001, TR-001, RTM-001 |
| 적용 한계 | 본 플랫폼은 2WD RC 데모. 아래 등급은 **표현(represented) 차량 기능 기준**으로 부여하고, 실제 RC 실물의 물리 심각도는 별도 주석(§3 비고)으로 구분한다. |

> **목적.** "기능이 고장·오작동했을 때 사람에게 가는 해(harm)"를 차량 레벨에서 식별하고, S/E/C로 등급화해 **ASIL과 Safety Goal**을 도출한다. SRS의 안전 요구(NFR-SAFE-*, FR-AB-*)는 *여기서 유도된 결과*여야 한다. (적이 있는 의도적 공격은 [TARA-001](TARA-001_Threat_Analysis_Risk_Assessment.md)에서 다룬다.)

---

## 1. 아이템 정의 (Item Definition)

HARA의 *입력*. 위험을 분석하려면 대상의 경계·기능·동작조건이 먼저 고정돼야 한다.

| 항목 | 내용 |
|---|---|
| 아이템 | 버튼 트리거 직진 주행 + 장애물 정지 차량 (DriveECU + SensorECU + CAN) |
| 주요 기능 | F1: 버튼 입력 시 직진 출발 / F2: 전방 장애물 10cm 감지 시 정지 / F3: A/B Secure OTA 업데이트 |
| 경계 | DriveECU(모터제어), SensorECU(HC-SR04), CAN 0x100/0x200/0x201, 부트로더. Gateway(RPi5)는 외부 |
| 동작 모드 | 부팅(BL) / IDLE / 주행 / OTA 다운로드 / OTA 활성화(재부팅) |
| 외부 인터페이스 | B1 버튼, HC-SR04, TB6612FNG 모터, CAN 버스 |

## 2. 등급 척도 (ISO 26262-3)

**S — 심각도 (Severity)**

| 등급 | 의미 |
|---|---|
| S0 | 부상 없음 |
| S1 | 경상~중경상 (AIS 1, 회복 가능) |
| S2 | 중상, 생존 가능 (AIS 3~6) |
| S3 | 치명상/사망 가능 (AIS 5~6) |

**E — 노출 빈도 (Exposure, 해당 동작상황에 놓일 확률)**

| 등급 | 의미 | 예 |
|---|---|---|
| E1 | 매우 낮음 | 거의 발생 안 함 |
| E2 | 낮음 | 드물게 |
| E3 | 중간 | 운전 중 가끔 |
| E4 | 높음 | 거의 매 주행 |

**C — 제어 가능성 (Controllability, 운전자/외부가 해를 회피 가능한가)**

| 등급 | 의미 |
|---|---|
| C0 | 일반적으로 제어 가능 |
| C1 | 쉽게 제어 가능 (99% 이상) |
| C2 | 보통 제어 가능 (90% 이상) |
| C3 | 제어 어려움/불가 |

**ASIL 결정 (ISO 26262-3:2018 Table 4).** 앵커: **S3·E4·C3 = D**. S·E·C 중 하나가 한 단계 낮아질 때마다 ASIL 한 단계 ↓ (하한 QM).

| S·E | C1 | C2 | C3 |
|---|:--:|:--:|:--:|
| **S3·E4** | B | C | **D** |
| S3·E3 | A | B | C |
| S3·E2 | QM | A | B |
| **S2·E4** | A | B | C |
| S2·E3 | QM | A | B |
| S2·E2 | QM | QM | A |
| **S1·E4** | QM | A | B |
| S1·E3 | QM | QM | A |

> 표에 없는(더 낮은) 조합은 QM. QM = 표준 품질관리로 충분, 별도 ASIL 안전요구 불필요.

## 3. HARA 분석표

각 행 = 한 위험 사건. **Safety Goal**이 최상위 안전요구이고, 거기서 FSR→SW 안전요구로 내려간다(§4).

| ID | 기능 | 동작상황 | 오작동 | 위험 사건 (차량 레벨 harm) | S | E | C | **ASIL** | Safety Goal | Safe State | FTTI |
|---|---|---|---|---|:--:|:--:|:--:|:--:|---|---|---|
| **H-1** | F2 장애물 정지 | 저속 직진 주행 중 전방 장애물 접근 | 장애물 감지 실패 또는 모터 미정지 | 차량이 장애물/보행자와 충돌 | S2 | E4 | C3 | **C** | 전방 10cm 장애물 감지 시 차량은 충돌 전 정지해야 한다 | 모터 정지 (NFR-SAFE-004) | 감지~정지 ≤ Tstop *(실측 유도)* |
| H-2 | F3 OTA 활성화 | 주행 중 OTA 활성화 조건 충족 | 주행 중 의도치 않은 재부팅/제어 상실 | 주행 중 갑작스런 거동/정지 불능 | S2 | E2 | C3 | **A** | OTA 활성화(재부팅)는 IDLE에서만 발생해야 한다 | 모터 정지 + 활성화 보류 | ← NFR-SAFE-001, FR-DRV-008 |
| H-3 | 부트로더 | 부팅(BL 실행) 단계 | BL 단계에서 모터 PWM 활성 | 부팅 중 의도치 않은 차량 이동 | S1 | E3 | C3 | **A** | 부트로더 실행 중 모터는 구동되지 않아야 한다 | 모터 출력 비활성 | ← NFR-SAFE-003 |
| H-4 | F3 A/B Slot | 업데이트/전원차단 후 첫 부팅 | 손상·미검증 이미지로 부팅 → 제어 로직 오류 | 차량 제어 불능 | S2 | E2 | C3 | **A** | 검증 통과한 이미지만 Boot Target이 된다(fail-closed) | 기존 Confirmed Slot 유지/Safe State | ← FR-AB-003, NFR-SAFE-004 |

**H-1 등급 근거 (워크드 예시):**
- **S2** — 저속 충돌이라도 보행자/사람 대상 시 중상 가능. *(RC 실물 비고: 경량 2WD·사람 없음 → 실제 S0~S1. 아래는 표현 기능 기준.)*
- **E4** — "장애물을 향해 접근하며 정지가 필요한 상황"은 이 차량 주기능이라 거의 매 주행 발생.
- **C3** — 본 설계는 운전자 개입 루프가 없는 자동 정지. 안전기능 실패 시 외부 회피 불가.
- → 표에서 **S2·E4·C3 = ASIL C**.

**H-2 등급 근거 (주행 중 의도치 않은 재부팅):**
- **S2** — 주행 중 제어 상실/정지 불능은 충돌로 이어질 수 있음(H-1과 동일 충돌 경로). 단 H-1보다 직접적 보행자 노출은 낮게 봄.
- **E2** — OTA 활성화는 정비/업데이트 시점에 한정. "주행 중 활성화 조건 충족"은 설계상 막혀 있어 드물게만 노출.
- **C3** — 재부팅 중에는 운전자/제어 루프가 개입 불가.
- → **S2·E2·C3 = ASIL A**. SG-2(활성화는 IDLE에서만)가 노출(E)을 구조적으로 억제하는 것이 핵심.

**H-3 등급 근거 (부트로더 단계 모터 구동):**
- **S1** — BL 단계는 정지 상태에서 시작하므로 발생해도 저속 미소 이동. 중상 가능성 낮음.
- **E3** — 부팅은 매 전원 인가/OTA 활성화마다 반드시 거치는 단계라 노출은 중간.
- **C3** — 부팅 중에는 운전자 입력 경로가 없어 회피 불가.
- → **S1·E3·C3 = ASIL A**.

**H-4 등급 근거 (미검증 이미지 부팅):**
- **S2** — 손상·변조 펌웨어로 제어 로직이 오동작하면 H-1과 동일한 충돌 경로로 전이 가능.
- **E2** — 업데이트/전원차단 직후 첫 부팅에 한정된 상황이라 노출은 낮음.
- **C3** — 이미 부팅된 손상 로직은 운전자가 사후에 제어하기 어려움.
- → **S2·E2·C3 = ASIL A**. fail-closed 검증(SG-4)이 이 위험을 차단하는 1차 방벽이며, 변조가 *공격*에 의한 경우는 [TARA-001](TARA-001_Threat_Analysis_Risk_Assessment.md) T-1/T-2로 연결된다(§5).

> ⚠️ Tstop(FTTI)·10cm·3-strike·8s IWDG 같은 **숫자는 여기 Safety Goal에서 유도**돼 SRS로 내려가야 한다. 지금 SRS는 이 숫자를 *선언*만 하고 있음 — 그 뿌리를 이 표가 채운다.

## 4. Safety Goal → 요구 내려보내기 (V의 왼쪽)

H-1을 끝까지 한 줄로 내려본 예시. **고도가 낮아지며 구체화**된다.

| 고도 | 항목 | 내용 | 추적 |
|---|---|---|---|
| 위험 사건 | H-1 | 장애물 충돌, ASIL C | 본 문서 §3 |
| **Safety Goal** | SG-1 | 10cm 장애물 감지 시 충돌 전 정지 | — |
| 기능안전요구(FSR) | FSR-1.1 | SensorECU는 ≤10cm 감지 시 CAN 0x200으로 통보 | FR-SEN-002 |
| FSR | FSR-1.2 | DriveECU는 장애물 통보 수신 시 모터를 정지한다 | FR-DRV-003 |
| **SW 안전요구(TSR)** | TSR-1.1 | `drive_update()` 주기 ≤ 10ms | NFR-PERF-003 |
| TSR | TSR-1.2 | 0x200 신호에 Alive Counter+CRC(E2E)를 적용해 stale/손상 프레임을 검출하고 검출 시 Safe State 진입 | 🔶 **갭 — SRS 미반영, 후속 보강 대상** (아래 갭 주석) |
| 설계/구현 | — | `motor_stop()`, 상태머신 | (구현 완료) |
| **검증(V 오른쪽)** | SIT-TC-04 | 통합: 0x200(장애물)→ DriveECU 모터 정지 확인. drive_sensor_fresh 픽스처로 실측 | [SIT-001](SIT-001_System_Integration_Test.md) · [TR-001](TR-001_Test_Report.md) |

> **드러난 갭:** TSR-1.2(E2E 보호)는 HARA를 돌려야 비로소 나온다 — 안전 관련 신호인 장애물 프레임에 freshness/CRC가 없으면 "센서가 죽어 마지막 '장애물 없음'을 붙들고 있을 때" 차가 못 선다. 이게 "톱다운 유도가 새 요구를 만든다"의 구체적 증거.

### 4.1 Safety Goal 종합 (위험 → SG → 요구 → 검증 → 상태)

각 H-위험에서 도출한 Safety Goal과, 그것을 구현·검증하는 요구/테스트의 연결을 한눈에 본다.

| SG | 위험 | ASIL | Safety Goal | 구현 요구 | 검증 | 상태 |
|---|---|:--:|---|---|---|:--:|
| SG-1 | H-1 | C | 10cm 장애물 감지 시 충돌 전 정지 | FR-SEN-002, FR-DRV-003, NFR-SAFE-004 | SIT-TC-04 (drive_sensor_fresh) | ✅ |
| SG-2 | H-2 | A | OTA 활성화(재부팅)는 IDLE에서만 발생 | NFR-SAFE-001, FR-DRV-008 | 단위(상태머신) + SIT 재부팅 시점 확인 | ✅ |
| SG-3 | H-3 | A | 부트로더 실행 중 모터 비구동 | NFR-SAFE-003 | 코드 검토(BL은 PWM 미초기화) | 🔶 |
| SG-4 | H-4 | A | 검증 통과 이미지만 Boot Target (fail-closed) | FR-AB-003/005/007, NFR-SAFE-004 | SIT-TC-07/08 (변조·미서명 거부) · TR-001 | ✅ |
| TSR-1.2 | H-1 | C | 0x200 안전신호 E2E(Alive+CRC) 보호 | *(SRS 미반영)* | — | 🔶 갭 |

> **상태 범례:** ✅ 검증 완료 · 🔶 부분 구현/검토 단계 또는 보강 대상. SG-1/SG-4는 [TR-001](TR-001_Test_Report.md)의 SIT 실행으로, SG-2는 상태머신 단위테스트로 확인. SG-3은 부트로더가 모터 PWM을 초기화하지 않는다는 코드 사실에 근거하나 별도 on-target 테스트는 미수행(🔶). TSR-1.2(E2E)는 본 HARA가 새로 드러낸 갭으로 SRS 후속 보강 대상.

## 5. 안전↔보안 브리지

H-1/H-2의 일부 원인은 *고장*이 아니라 *공격*일 수 있다 (예: 변조 펌웨어로 모터 폭주). 그 경로는 [TARA-001](TARA-001_Threat_Analysis_Risk_Assessment.md)의 피해 시나리오로 연결되며, **TARA의 Safety 영향 등급은 본 HARA의 위험 사건을 참조**한다. 보안 침해 → 안전 위험의 전이가 이 프로젝트의 핵심 논지다.

## 6. 채우는 순서 (사용법)

1. §1 아이템 정의를 네 시스템에 맞게 확정.
2. §3에서 동작모드별 오작동을 브레인스토밍 → 위험 사건(차량 레벨 harm)으로 표현.
3. 각 사건에 S/E/C 부여 + **근거 한 줄**(H-1처럼). 근거 없는 등급은 무효.
4. §2 표로 ASIL 산출 → Safety Goal 작성(+Safe State+FTTI).
5. §4처럼 각 Goal을 FSR→TSR로 내려 **기존 SRS ID에 연결**. 연결 안 되면 그 요구는 근거 없는 것 → SRS 보완 대상.
