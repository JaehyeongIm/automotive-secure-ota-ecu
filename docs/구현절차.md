## Phase 1 — CAN 버스 통신 검증 ✅ 완료

**목표:** STM32 두 보드가 CAN으로 실제 통신하는 것 확인

- STM32CubeIDE 프로젝트 생성 (F446RE ×2, DriveECU / SensorECU)
- 하드웨어 연결

```
STM32 #1 --- SN65HVD230 ---[120Ω]--- SN65HVD230 --- STM32 #2
                               |
                           CANable --- PC (USB)
```

- CAN 핀: PA11 (CAN1_RX), PA12 (CAN1_TX)
- 버스 양 끝단에 120Ω 종단저항 각 1개
- PC 측 툴 설치

### 하드웨어 배선 절차

**각 Nucleo → SN65HVD230 연결 (×2)**

| Nucleo 핀 | SN65HVD230 핀 | 비고 |
|---|---|---|
| PA12 (CAN1_TX) | CTX | 데이터 송신 |
| PA11 (CAN1_RX) | CRX | 데이터 수신 |
| 3.3V | VCC | 트랜시버 전원 |
| GND | GND | 공통 그라운드 |

**CAN 버스 (브레드보드)**

```
DriveECU                         SensorECU
SN65HVD230                       SN65HVD230
  CANH ─┬────────────────────────┬─ CANH
  CANL ─┼────────────────────────┼─ CANL
        │                        │
       [120Ω]              [120Ω]  ← 버스 양 끝단 종단저항
        │                        │
       GND                      GND
```

**CANable 연결**

| CANable 단자 | 연결 대상 |
|---|---|
| CANH | 버스 CANH 라인 |
| CANL | 버스 CANL 라인 |
| GND | 공통 GND |
| USB | PC |

**GND 공통 연결 필수**
- DriveECU GND, SensorECU GND, CANable GND 모두 브레드보드 GND 레일에 연결

**전원 인가 순서**
1. USB → DriveECU, SensorECU (PC 연결)
2. CANable USB → PC

**정상 동작 확인**
- 두 보드 모두 LD2(녹색) 깜빡임 → CAN 메시지 송신 중
- 각 보드 UART 터미널에 상대방 ID 수신 로그 출력

```bash
pip install python-can   # CANable → slcan 인터페이스로 인식
```

- CAN Loopback 테스트 (단일 보드 자가 송수신) → 두 노드 양방향 통신 테스트 → CANable PC 모니터링
- 오실로스코프로 CAN_H/CAN_L 파형 확인 (500Kbps 검증)

## Phase 3 — Bootloader 구현 ✅ 완료

**목표:** 전원 인가 시 유효한 Slot을 선택해 점프하는 Bootloader

- Flash 레이아웃 설계 (F446RE 512KB 기준)

```
주소          영역                크기   섹터
0x08000000  Bootloader Area     32KB   섹터 0(16KB) + 섹터 1(16KB)
0x08008000  Metadata Area       16KB   섹터 2
0x0800C000  Reserved            16KB   섹터 3
0x08010000  Slot A Application  192KB  섹터 4(64KB) + 섹터 5(128KB)
0x08040000  Slot B Application  256KB  섹터 6(128KB) + 섹터 7(128KB)
```

- Metadata 구조체: magic, active_slot, slot_a/b_status, slot_a/b_version, boot_count, slot_a_size, slot_b_size
- 부팅 로직: Metadata 확인 → CONFIRMED/PENDING Slot 선택 → Stack Pointer 유효성 검사 → ECDSA-P256 서명 검증 → App jump
- IWDG 시작 (Prescaler 256, Reload 999 → 약 8초): App이 kick하지 않으면 리셋
- 검증 실패 시 Safe State (UART 출력 + IWDG kick 루프)

**미구현 사항:**
- boot_count 3회 초과 시 반대 Slot 폴백
- WRP(Write Protection) Sector 0~1 활성화

## Phase 4 — UDS + ISO-TP + OTA 프로토콜 ✅ 완료

**목표:** A/B OTA — ECU가 비활성 슬롯을 자동 선택하여 펌웨어 업데이트

- ISO-TP 구현 (STM32 측 수신 처리)
  - Single Frame / First Frame / Consecutive Frame / Flow Control
  - STmin=0, BlockSize=0, N_Bs=1000ms
- UDS 서비스 구현 (DriveECU)
  - `0x10` DiagnosticSessionControl
  - `0x27` SecurityAccess (Seed XOR 0xDEADBEEF)
  - `0x34` RequestDownload — addr=0: ECU가 `ota_get_active_slot()`으로 비활성 슬롯 자동 선택
  - `0x36` TransferData (256 byte 청크)
  - `0x37` RequestTransferExit → `ota_meta_write_pending(slot, fw_size)` → NVIC_SystemReset
- OTA 클라이언트 (`tools/ota_client.py`) — Slot 주소 하드코딩 제거, ECU 자동 선택 위임
- E2E 테스트 완료: RPi5(can0) → DriveECU A/B OTA → ECDSA OK → 신규 슬롯 부팅

**A/B 슬롯 동작 원리:**
```
active_slot=0(A) → OTA 타겟=Slot B → firmware_slotb.bin(0x08040000 링크)
active_slot=1(B) → OTA 타겟=Slot A → firmware_slota.bin(0x08010000 링크)
```
클라이언트는 항상 동일한 명령 전송, 타겟 슬롯 결정은 ECU 책임.

**트러블슈팅 기록:**
- VTOR 하드코딩 문제 → `g_pfnVectors` 링커 심볼로 해결 (`main.c` USER CODE BEGIN 1)
- python-can slcan DLC 파싱 버그 → `.venv/.../slcan.py` line 282 패치
- ARM inline asm `-mthumb` 호환 문제 → `uECC_PLATFORM=0`으로 순수 C 강제
- 상세 내용: `docs/troubleshooting/phase4_driveECU_bootloader_can_interrupt.md`

## Phase 5B — ECDSA 서명 파이프라인 ✅ 완료

**목표:** 서명된 펌웨어만 Bootloader가 수락

### 구현된 서명 포맷 (Appended Signature)

SRS 13.1의 manifest.json 방식 대신, 바이너리 말미에 서명을 직접 붙이는 방식으로 구현:

```
┌───────────────────────────────┐
│  firmware binary  (N bytes)   │  ← SHA-256 해시 대상
├───────────────────────────────┤
│  ECDSA-P256 sig   (64 bytes)  │  ← r(32) || s(32), big-endian
└───────────────────────────────┘
         총 (N + 64) bytes
```

Metadata의 `slot_*_size` = 총 바이너리 크기(N + 64), Bootloader가 마지막 64바이트를 서명으로 인식.

### 키 생성 (개발 PC에서 1회)

```bash
openssl ecparam -name prime256v1 -genkey -out keys/private_key.pem
# 공개키는 tools/sign_firmware.py 실행 시 자동 출력되는 C 배열을
# Bootloader/Core/Inc/ecdsa_pubkey.h 에 복사
```

- `keys/private_key.pem`: Git 커밋 금지 (`.gitignore` 등록), Jenkins Credentials에만 보관
- `ecdsa_pubkey.h`: Bootloader 이미지에 하드코딩 (공개키이므로 노출 무방)

### `tools/sign_firmware.py` (구현 완료)

```bash
python3 tools/sign_firmware.py DriveECU_SlotB.bin keys/private_key.pem \
    --out firmware_slotb_signed.bin
```

출력: `firmware_slotb_signed.bin` = 원본 바이너리 + 64바이트 서명

### Bootloader ECDSA 검증 (`bootloader.c`, 구현 완료)

- micro-ecc 라이브러리 (secp256r1, `uECC_PLATFORM=0` 순수 C)
- SHA-256 라이브러리 (`Bootloader/Core/Lib/sha256.c`)
- 검증 흐름:
  1. `slot_*_size`(N+64)에서 N = `fw_total - 64` 계산
  2. Flash[boot_addr .. boot_addr+N-1] 구간 SHA-256 해시
  3. Flash[boot_addr+N .. boot_addr+N+63] 를 서명으로 `uECC_verify()` 호출
  4. 실패 시 `safe_state()` 진입
- `size==0` 또는 `size > slot_max`: ST-Link 직접 플래싱 호환을 위해 검증 건너뜀

**검증 완료 (UART 로그):**
```
[BL] ECDSA OK
[DriveECU v2] Start
```

## Phase 6A — RC카 + Drive ECU 라인트레이싱 ❌ 미완료

### 하드웨어 배선

**TB6612FNG 모터 드라이버 (DriveECU)**

| DriveECU 핀 | TB6612FNG 핀 | 비고 |
|---|---|---|
| TIM (PWM A) | PWMA | 좌측 모터 속도 |
| TIM (PWM B) | PWMB | 우측 모터 속도 |
| GPIO | AIN1/AIN2 | 좌측 모터 방향 |
| GPIO | BIN1/BIN2 | 우측 모터 방향 |
| 3.3V | STBY | Standby 해제 |
| VM | 모터 전원 (배터리) | |

**라인트레이서 센서 (TCRT5000 3채널)**

| 센서 채널 | DriveECU 핀 | 비고 |
|---|---|---|
| 좌측 | ADC1_IN0 | PA0 |
| 중앙 | ADC1_IN1 | PA1 |
| 우측 | ADC1_IN4 | PA4 |

### Drive ECU App v1 — ON/OFF 제어

- 중앙 센서가 라인 감지 → 직진
- 좌측 센서 감지 → 좌회전 (좌모터 정지, 우모터 구동)
- 우측 센서 감지 → 우회전
- OTA 세션 진입 시 PWM 출력 차단 (NFR-SAFE-001)

### Drive ECU App v2 — 비례 제어

- 3채널 센서 가중 합산으로 편차(error) 계산
- `PWM_duty = base_speed ± Kp * error` (P 제어)
- 곡선 구간 이탈 횟수 감소 또는 랩타임 단축 목표 (TC-NOR-006)

**0x100 CAN 메시지 페이로드 업데이트:**

| Byte | 내용 |
|---|---|
| 0 | app_version (1 또는 2) |
| 1 | active_slot (0=A, 1=B) |
| 2 | driving_state (0=정지, 1=주행) |
| 3 | obstacle_flag (0x200 수신 여부) |
| 4~7 | tx_count (기존 유지) |

## Phase 6B — SensorECU 완성 ❌ 미완료

**목표:** 장애물 감지 메시지 송신 + OTA 수신

### HC-SR04 거리 측정

| 핀 | SensorECU 핀 | 비고 |
|---|---|---|
| Trigger | GPIO Output | 10us pulse |
| Echo | TIM InputCapture | 펄스 폭 측정 |

- 측정 거리(cm) = Echo 펄스 폭(us) / 58
- 설정 임계값 이하 감지 시 0x200 CAN 메시지 송신

**0x200 CAN 메시지 페이로드:**

| Byte | 내용 |
|---|---|
| 0 | obstacle_detected (0x01=감지, 0x00=없음) |
| 1 | distance_cm |
| 2~3 | 예약 |

**Drive ECU 연동:**
- 0x200 수신 → obstacle_flag 세트 → PWM duty 감소 또는 정지 (NFR-SAFE-002)

### SensorECU OTA 구현

DriveECU 구현을 포팅 (CAN ID만 교체):

| 항목 | DriveECU | SensorECU |
|---|---|---|
| UDS Request CAN ID | 0x7E0 | 0x7E1 |
| UDS Response CAN ID | 0x7E8 | 0x7E9 |
| Slot A 주소 | 0x08010000 | 0x08010000 (동일) |
| Slot B 주소 | 0x08040000 | 0x08040000 (동일) |

- `isotp.c`, `uds.c`, `ota_flash.c` SensorECU 프로젝트에 추가
- Linker Script: DriveECU와 동일 구조 사용
- Bootloader: 동일 바이너리 재사용 가능

**SensorECU App v1/v2 차이:**
- v1: 임계값 15cm 이하 장애물 감지
- v2: OTA 후 임계값 25cm으로 변경 (TC-NOR-007)

## Phase 5C — Jenkins CI/CD ❌ 미완료

**목표:** Git push → 빌드 → 서명 → OTA 자동화 (SRS FR-CICD-001~009)

### RPi5에 Jenkins 설치
docker 아닌 직접설치

### arm-none-eabi-gcc 크로스컴파일 환경

```bash
sudo apt install gcc-arm-none-eabi
arm-none-eabi-gcc --version  # 확인
```

### Jenkinsfile (5단계)

```groovy
pipeline {
  agent any
  stages {
    stage('Build') {
      steps { sh 'make -C DriveECU' }
    }
    stage('Static Analysis') {
      steps { sh 'cppcheck --error-exitcode=1 DriveECU/Core/Src/' }
    }
    stage('Size Check') {
      steps { sh 'python3 tools/check_size.py DriveECU.bin 131072' }  // 128KB
    }
    stage('Sign') {
      steps {
        withCredentials([file(credentialsId: 'ecdsa-private-key', variable: 'KEY')]) {
          sh 'python3 tools/sign_firmware.py DriveECU.bin $KEY'
        }
      }
    }
    stage('Deploy OTA') {
      steps { sh 'python3 tools/gateway.py --manifest manifest.json' }
    }
  }
}
```

**검증 (TC-CICD-001~003):**
- 빌드 오류 또는 128KB 초과 시 파이프라인 중단
- 서명 및 manifest 생성 아티팩트 확인
- OTA 배포 후 ECU 응답 로그 확인

## 권장 진행 순서

```
[완료] Phase 1~4, 5A, 5B
  → Phase 6A (RC카 조립 + Drive ECU 라인트레이싱)  ← 현재 단계
```
