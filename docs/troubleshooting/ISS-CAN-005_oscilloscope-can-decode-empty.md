# ISS-CAN-005: 오실로스코프 CAN 디코드 이벤트표가 비어있음 (통신은 정상)

> ⚠️ **관측성(계측) 이슈** — 제품 결함이 아니다. CAN 버스·펌웨어는 전 과정 정상이었고, 원인은 모두 오실로스코프(DHO804) 측 설정이었다.

| 항목 | 내용 |
|---|---|
| 증상 | UART로는 CAN 통신이 확인되는데, 오실로스코프 CAN 디코드 이벤트표가 계속 비어있음 |
| 상태 | ✅ 해결됨 |
| 심각도 | Low (관측성/툴링 — DUT 결함 아님) |
| 영향 | on-target 벤치 CAN 파형 관측·디코드 (Rigol DHO804). 제품 동작엔 영향 없음 |
| 관련 | SIT-001(테스트 플랜) · 벤치 구성(DriveECU↔SensorECU, 500kbps CAN) |

---

## D2. 문제 정의 (5W2H · Is–Is Not)

- **무엇이**: DHO804로 CAN_H/CAN_L를 프로빙했으나 ① 처음엔 파형 자체가 0V로 안 보이고, ② 파형이 보인 뒤에도 CAN 디코드 이벤트표가 비어있었다.
- **어디서**: on-target 벤치, 두 노드(DriveECU↔SensorECU) 간 500kbps 표준 CAN. 트랜시버 버스측 CAN_H/CAN_L을 브레드보드에서 프로빙.
- **언제**: 스코프로 OTA/벤치 트래픽을 관측하려고 디코드를 설정하는 동안.
- **얼마나**: 디코드 이벤트표 0건. 동시에 UART 로그·노드 간 통신은 정상.

**Is ↔ Is Not (원인 범위 좁히기)**

| Is (문제 발생) | Is Not (정상) |
|---|---|
| 스코프 화면/디코드에서 안 보임 | 멀티미터 DC 측정은 CAN_H/CAN_L = 2.4V (정상 recessive) |
| 스코프 관측 실패 | 두 노드 통신 자체는 성공 (UART 확인) → 버스/펌웨어 정상 |
| 단발 프레임은 디코드됨(설정 수정 후) | 연속 다중 프레임은 별도 설정 필요 |

→ **멀티미터 2.4V vs 스코프 0V**라는 불일치가 "버스가 아니라 스코프 측 문제"임을 가리켰다.

**재현 절차**
1. 두 노드 전원 인가, 500kbps CAN 통신 시작.
2. DHO804 프로브를 CAN_H(CH1)/CAN_L(CH2)에 연결, CAN 디코드 설정.
3. 이벤트표가 비어있음을 확인.

---

## D4. 근본 원인 분석 (RCA)

기법: **5 Whys** + **Is–Is Not** + 분기 측정(bisecting measurement)으로 가설을 하나씩 배제.

순차적으로 **두 개의 독립 근본 원인**이 겹쳐 있었다(앞의 것을 고치자 다음 것이 드러남).

### 근본 원인 ① — 프로브 감쇠비 불일치 (신호가 0V로 보임)

- **증상**: CAN_H/CAN_L 모두 0V 평선, Math는 0 근처 잡음. 멀티미터는 2.4V.
- **분기 측정**: 멀티미터 DC로 CAN_H↔GND = 2.4V → 버스는 정상 recessive(2.5V). 문제는 스코프 측으로 확정.
- **5 Whys**:
  1. 왜 0V? → 스코프에 들어온 신호가 매우 작아서.
  2. 왜 작아짐? → 프로브 물리 스위치 = **10×**(신호를 1/10로 감쇠).
  3. 왜 표시가 안 됨? → 스코프 채널 Probe ratio = **1×** (감쇠된 0.25V를 그대로 표시).
  4. 왜 불일치? → 둘은 별개 설정인데 서로 안 맞춰짐.
  5. 결과 → 실제 2.5V가 0.25V로 표시되어 1V/div에서 평선처럼 보임.
- **근본 원인**: **프로브 물리 스위치(10×)와 스코프 Probe ratio(1×) 불일치.**
- **배제한 가설(Is Not 근거)**:
  - AC 커플링 → DC 확인했으나 변화 없었고, 실제론 비율 문제였음.
  - 접지 클립 부유 → 공통 GND 연결 확인됨.
  - CAN 루프백 모드 → 두 노드 실통신(2.4V 바이어스)로 배제.
  - 프로빙 위치 오류(MCU측 TX/RX) → CAN_H/CAN_L에서 2.4V 측정으로 배제.

### 근본 원인 ② — 타임베이스 과속 (완전한 프레임 미캡처 → 디코드 0건)

- **증상**: 파형은 정상으로 보이고 디코드 설정(아래)도 전부 정상인데 이벤트표가 빔.
  - 버스종류 CAN · 전송속도 500kbps · 신호 CAN_H · 임계값 3.12V · 샘플위치 50% · 이벤트표 ON.
- **분기 측정 1 (클럭 배제)**: 화면에서 1비트 폭 측정 = 평평한 한 칸 **1.893µs**.
  - 브레드보드 에지 천이시간(~100ns)을 감안하면 ≈ **2.0µs = 500kbps**. 528k 등 어중간값은 클럭 트리상 불가(47.5MHz APB1 불가능).
  - 클럭 체인 정상 확인: HSE 8MHz(ST-Link MCO, **BYPASS**) → PLL → SYSCLK 180MHz → APB1 **÷4 = 45MHz** → 비트 = tq200ns × 10 = 2µs. **보드레이트 불일치 아님.**
- **분기 측정 2 (임계 배제)**: CAN_H 도미넌트 실측 3.78V, recessive 2.5V → 임계 3.12V(중간). 그래도 0건 → 임계 문제 아님.
- **핵심 발견**: 타임베이스가 빨라 취득 창에 **프레임 일부만** 담겼다. 디코더는 취득 메모리(캡처된 샘플)를 사후 해석하므로, **완전한 프레임(SOF→EOF)이 캡처 시간폭 안에 통째로 들어와야** 유효 프레임이 된다. 부분 프레임은 CRC·EOF 불성립 → 이벤트표 0건.
- **근본 원인**: **타임베이스 과속으로 완전한 프레임이 취득 창에 들어오지 못함.**

## D5–D6. 시정 조치 & 검증

**시정 조치**
1. (①) 프로브 물리 스위치를 스코프 Probe ratio와 **일치**시킴(1×↔1×). → CAN_H 2.5V 유휴·도미넌트 천이 정상 표시.
2. (②) **타임베이스를 느리게**(프레임 전체가 화면에 들어오게) 조정. 필요 시 메모리 깊이 확대.
3. 디코드 임계값 = CAN_H 도미넌트/리세시브 실측 중간(3.12V).

**검증**: D2 재현 절차로, SINGLE 캡처 시 이벤트표에 프레임 1건 표시됨.
```
index: 1   time: 2.856µs   id: 0x01F   (DLC/Data/CRC/ACK 칼럼 동반)
```
→ 증상 해소 확인. (다중 프레임은 메모리 깊이↑ + 타임베이스↓로 한 창에 여러 프레임 수용.)

## D7. 재발 방지 (Lessons Learned)

**스코프 CAN 디코드 체크리스트** (이벤트표가 빌 때 순서대로)

1. [ ] **프로브 물리 스위치 = 스코프 Probe ratio** 일치 (불일치 시 전압 10배 오차/평선)
2. [ ] 채널 **DC 커플링** (AC면 2.5V 바이어스가 잘려 0V 기준선)
3. [ ] 공통 GND에 접지 클립 연결
4. [ ] 화면에서 **1비트 폭 측정**으로 실보드레이트 확인 (500k=2µs). CubeMX 공칭값이 아닌 실측 기준.
5. [ ] 디코드 **소스 채널**이 CAN_H 파형 채널인지, **신호=CAN_H**(극성) 일치
6. [ ] 임계값 = 도미넌트/리세시브 실측 **중간값**
7. [ ] **타임베이스를 완전한 프레임이 들어오게** (가장 흔한 최종 원인). 다중 프레임은 메모리 깊이↑

**핵심 교훈**
- **분기 측정으로 범위부터 좁힌다**: 멀티미터 DC(2.4V) vs 스코프(0V) 한 번으로 "버스 아님, 스코프임"이 확정됐다. 가설을 난사하기 전에 갈림길을 만드는 측정을 먼저.
- **스코프 디코더 = 캡처된 한 토막의 사후 해석**(실시간 버스 청취가 아님). 완전한 프레임이 취득 시간폭(타임베이스×칸수) 안에 들어와야 디코드된다. 이벤트표는 **최신 1회 캡처**로 갱신되며 누적 로그가 아니다 — 전수 로깅은 CAN 분석기(SocketCAN/candump)의 몫.
- **공칭값 ≠ 실측값**: CubeMX "500k"는 가정 클럭(APB1 45MHz) 기준 공칭값. 실보드레이트는 파형의 비트 폭으로 검증한다.
